What the distance model does inside

A trajectory-level analysis of the recall-flow model that predicts shortest-path distance in a factored world with movement guards. The question: the total predicted distance is a sum over factors of each factor's internal displacement — does each factor's displacement reflect the distance that factor actually has to travel? Answer: in a good fraction of trained models, yes — and we can see exactly how.

01Setup, in plain terms

The world has several independent "factors," each a position on a small cycle. Some factors are guarded: a factor can only move while the factor before it sits at a special unlock position (position 0). So getting from one configuration to another sometimes forces a factor to detour to the unlock cell to free the next one. The model reads a start and a goal and predicts the true shortest-path distance between them.

Internally it runs a small looped network for several steps, nudging an internal token for each factor toward the goal. The predicted distance is the total amount those tokens move: distance = sum over factors of c_i, where c_i is how far factor i's token travels across the loop. We logged those per-factor trajectories on ~1500 start/goal pairs and compared them to the ground truth. Analysis is on a trained checkpoint (n=5 factors, 6-cycles, chain guards, trained on distances up to 20). All numbers reproducible from analyze_traj.py.

02The core result — per-factor cost tracks the REAL per-factor travel

Left: each factor's cost c_i vs the number of moves that factor actually makes in the true shortest path — correlation 0.94 (per factor: 0.97–0.99). Middle: the same cost vs the naive "cycle distance" (shortest arc ignoring guards) — correlation 0.13. Right: total cost vs true geodesic — a perfect line (r=1.0, error 0.1 moves).

Answer to the hypothesis

Yes — the per-factor displacement reflects the distance each factor must traverse, but the guard-aware traversal (the real path moves), not the raw cycle arc. The two differ because an internal factor often must move to the unlock cell to free its descendants, so it travels more than its own arc. The model charges exactly that. The one factor whose cost equals its cycle distance is the leaf (nothing depends on it, so it only moves for itself). Internal factors each take ~1.3 extra "unlock" moves, and the model's cost includes them.

03How it computes it — an amortized jump, not a walk

(plot missing)

The model does not slowly trace the path. It commits almost immediately: ~90% of all internal movement happens in the first 3 steps, then it parks. The distance is encoded in the size of that jump, not in a number of steps — which is exactly why it extrapolates to far distances at a fixed compute budget (extra steps add nothing). It is an amortized distance oracle.

04But the jump routes through the unlock cell

Even though it jumps, the brief transient is not blind. When a factor must unlock a descendant, its token visits the unlock position (0) during the transient 96% of the time; when it does not need to, only 36%. So the internal process encodes the guard-routing — it "passes through" the unlock exactly when the structure requires it, then snaps to the goal.

But the routing is spatial, not temporal. Left: each factor's cost is a near-linear count of its true path-moves — calibration slope ≈ 0.85 (so the cost literally counts moves, slightly under 1:1). Right: the parent reaches the unlock cell before the child moves only 17–25% of the time (median step-gap zero) — the parent's visit to the unlock cell and the child's move happen in the same jump. So the flow does not re-enact the guarded path step by step; it routes tokens through unlock cells spatially, all at once, in one amortized jump.

05It is not geometric distance in the embedding

The six position embeddings are not arranged in a clean circle (embedding-distance vs cycle-distance correlation only 0.38). So the model is not reading off a geometric map; the flow dynamics compute the distance.

06The honest caveat — it is not the only solution

Every competent model predicts the total perfectly and extrapolates well, but the clean per-factor decomposition above is seed-dependent. Retrain the same configuration with a different seed and you sometimes get an entangled internal solution: per-factor costs are redistributed (total still exact) with no unlock-routing. Among well-trained n=5 models we saw roughly half clean, half entangled.

Crucially, clean-ness barely predicts extrapolation quality (correlation −0.32): an entangled model extrapolates just as well. So the clean per-factor structure is real but not load-bearing — the model's accuracy does not depend on decomposing cleanly. (Undertrained, small-range models are both entangled and weak; image-input models entangle the decomposition further.)

How the entangled solution redistributes cost. In entangled models each factor's cost correlates with the global total distance about as much as with its own moves (roughly 0.3-0.7 either way), whereas in clean models the cost tracks the factor's own moves strongly (0.94-0.99) and the total only weakly. So the entangled solution smears the cost across factors - an exact sum without a clean per-factor attribution - while the clean solution assigns each factor exactly its own traversal. Same total, two different internal bookkeepings.

07Summary of the internal process

  • Total = geodesic, exactly (r=1.0, ~0.1 move error), and it is a sum of per-factor displacements.
  • In "clean" models, each factor's displacement equals its true guarded-path travel (0.94–0.99), including the extra moves internal factors make to unlock descendants. This is where your hypothesis holds.
  • The flow is an amortized oracle: it jumps to the answer in ~3 steps and parks; the distance is in the jump magnitude, not a step count.
  • Its transient routes through the unlock cell exactly when the guard requires it (0.96 vs 0.36).
  • Distance is computed by the dynamics, not geometry (embeddings are non-metric).
  • Clean-ness is seed-dependent and not required for accuracy — competent models also solve it entangled. So "per-factor cost reflects per-factor travel" is a property some trained solutions have, not a law.
